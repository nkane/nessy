# ADR 0009 — v1.0.0: the production cut — debugger, accuracy close-out, MMC5, release pipeline

- **Status:** Accepted (release candidate — the tag is gated on the #7 headliner playtest + the #8 stable-release secrets; the code + decisions below are complete and merged to `main`)
- **Release:** v1.0.0 (2026-07-10)
- **Theme:** Turn the post-carve emulator into a production release — a Mesen2-parity inspection debugger, the accuracy ROM suite closed out, the last major commercial mapper (MMC5), a signed multi-platform release pipeline, a perf regression gate, and a full browser playground. Tracked under the v1.0 epic ([issue #13](https://github.com/nkane/nessy/issues/13)).

## D1 — TUI debugger: NES state + controls over DAP custom requests; chippy renders the panels

- **Context:** the chippy DAP + TUI already covers the CPU side (step / breakpoints / watch / memory / stack / source). What v1.0 needs is everything *NES-specific* — PPU/OAM/palette viewers, per-space memory + access heatmaps, an event viewer, typed breakpoints, register/APU state, trace logging — none of which the 6502 core can see. Building a second GUI stack was never on the table.
- **Decision:** keep the UI a **TUI modelled on the chippy debugger** and split the work along the repo boundary. **nessy exposes NES debug state + the new step/breakpoint/trace controls as DAP custom requests** (`nessy/*`), each served from a paused-snapshot so a panel never reads a half-stepped machine; **chippy renders the panels** that consume them. nessy lands the data + protocol first (the snapshot channel + panel host, #28) so the TUI has something to draw. The panels consume chippy's **v1.5.0 host hooks** (chippy#419): `cpu.SetAccessHook` + `AccessKind` (heatmap), `RAM.Freeze/Unfreeze` (freeze), `dap.Server.SetHostVars` (NES-aware breakpoint conditions), `SetStopPredicate` (NES step granularity). `AttachConfig.CustomRequestHandler` (v1.4.0) is the seam the `nessy/*` handlers hang off.
- **Consequences:** the whole v1.0-core panel set shipped (PPU viewer #29, sprite/OAM #30, event viewer #31, memory viewer #32, breakpoints + step granularity #33, register/APU #34, trace logger #35, heatmap + freeze #41), closing the #27 umbrella. The division keeps nessy free of any TUI-rendering code and keeps the debug surface a versioned protocol rather than a shared type. Full-parity extras (Lua / profiler / assembler / CDL / symbol import) are explicitly **post-1.0** (#36).

## D2 — Typed breakpoints latch at the register's owner; NES step modes are host stop-predicates

- **Context:** chippy's breakpoints see the CPU address bus, but the interesting NES breakpoints are on register spaces the CPU bus alone can't distinguish — PPU registers ($2000-$2007), the PPU bus ($0000-$3FFF), and the CPU register window ($4000-$4017: APU + $4014 OAMDMA + $4016/$4017 joypad). And "run to the next scanline / frame / NMI / IRQ" isn't expressible as an address breakpoint at all.
- **Decision:** **each component checks breakpoints on the accesses it owns.** The PPU checks its own register + bus breakpoints (#49); the **$4000-$4017 breakpoints live at the `dmaBus` chokepoint** every CPU MMIO access already passes through (the #20 DMA-glitch wrapper), suppressed during a DMC/OAM DMA fetch so the DMA unit's own reads don't trip a user break (#53). A match **latches a `pendingStop`**; `nessy/armBreakpointStop` wires a host stop-predicate that drains both sinks, halting the run at the next instruction boundary. **NES step granularity** (`nessy/stepScanline`, `stepFrame`, `runToNMI`, `runToIRQ`) arms `SetStopPredicate` with a small closure over live PPU/CPU state. **run-to-IRQ** samples `(IRQAsserted() && I-flag clear)` — the level the 6502 uses to take a hardware IRQ — so it needs **no chippy change**, and cleanly excludes BRK (a software opcode) and NMI (its own line).
- **Consequences:** the typed-breakpoint surface is complete across all three register spaces plus the four step modes, gated by has-flags so an access costs nothing until a breakpoint is armed. Because run-to-IRQ rides only the public `IRQAsserted()` + `P`/`FlagI`, the debugger didn't force a chippy release. Closed #49 + #53.

## D3 — Five accuracy-grading paths for ROMs with no `$6000` shell

- **Context:** the Blargg `$6000` status protocol (`runBlargg`, ADR 0007) only covers the newer test ROMs. The gate ROMs for sprite-0 / sprite-overflow / dmc_dma / the MMC5 mapper report differently — some park with a zero-page result byte, some self-calibrate to a terminal hang, some only print a verdict to the nametable, and some are interactive with no self-report at all.
- **Decision:** grow the harness from one grading path to **five**, dispatched per ROM in `cmd/nessy/accuracy_test.go`: `runBlargg` ($6000 shell); `runParkedResult` (run to the CPU's self-loop park, read a zero-page result byte — sprite_overflow / sprite_hit, #19/#21); `runTerminalLoop` (converge to a fixed terminal-hang PC window — dma_2007_read, #20); `runScreenText` (decode the nametable as ASCII, pass on "PASSED" — cpu_timing_test6, #21); and `gradeScreenGolden` (step a fixed frame count, encode the framebuffer as a brightness-ramp ascii grid, diff a committed golden — the interactive MMC5 test ROM, #6). All GPL ROMs stay **downloaded + sha256-pinned**, never vendored (ADR 0008 D3). The **dmc_dma #20** case was root-caused by a from-boot `(PC, cycle)` diff against a headless MesenCE reference: chippy's `idle()` didn't poll `ProcessPendingDma`, so a DMA halt armed into a taken-branch dummy-read cycle drained one cycle late — fixed chippy-side (#497), plus the host-owned open-bus glitch formula in `dmaBus`.
- **Consequences:** the accuracy tracker (#1) is green or tracked-knownFail for every wired ROM — sprite_overflow, sprite_hit, oam_read/stress, ppu_open_bus, mmc3_test 1-6, dmc_dma, cpu_timing_test6, and the MMC5 screen golden. The five paths are the executable record that the cycle-precision work still holds; a real regression in any passing ROM fails CI. Closed #4 / #12 / #17-21 / #25.

## D4 — MMC5 through a widened PPU↔cart seam of narrow optional interfaces

- **Context:** MMC5 (mapper 5 — Castlevania III US) is the last major commercial mapper, and the most capable NES ASIC: PRG/CHR banking, a 1 KiB ExRAM with several modes, per-quadrant nametable control, extended-attribute CHR override, a scanline IRQ, a hardware multiplier, and two expansion audio channels. Most of that needs a richer PPU↔cart conversation than the existing `Cartridge` interface (bank reads + a static `Mirroring()`).
- **Decision:** implement it in phases behind **narrow optional interfaces the PPU type-asserts on its cart** — `nametableMapper` (per-quadrant CIRAM / ExRAM / fill routing), `scanlineNotifier` (the in-frame IRQ counter), `chrContext` (sprite-vs-BG fetch phase for the 8×16 dual CHR banks), and `extAttrMapper` (ExRAM extended attributes) — plus a `cart.MMC5AudioSink` for the $5000-$5015 audio, mirroring how VRC6/5B/VRC7 audio attaches. Phase 1 was the CPU-side register file + banking + multiplier + ExRAM (#57); phases 2a-2d added the four PPU-integration surfaces (#67-70); audio landed separately (#56). The chip revision, where it matters, is keyed by content hash — the same pattern MMC3 rev-A/B uses.
- **Consequences:** MMC5 boots + renders + plays (verified by the #6 screen-golden gate + eyeball of the CHR-bank and ExRAM-execution test ROMs). The optional-interface seam keeps the `cart` package free of PPU imports — a cart that doesn't implement an interface simply isn't asked — and is now the template for any future mapper that needs PPU-fetch context. Closed #6.

## D5 — Validate the non-linear DAC by property, not by a false-passing ROM

- **Context:** the non-linear DAC mixer shipped pre-1.0 (`mixer.go` + `emitSample`). The remaining #5 task was to validate it against Blargg's `apu_mixer`. But probing all four `apu_mixer` ROMs headlessly showed they report status `$00` = *completed* with purely instructional text ("Should be nearly silent") — they cancel the channel-under-test against the DMC DAC to near silence and leave a **human ear as the oracle**. There is no programmatic verdict.
- **Decision:** do **not** wire `apu_mixer` into the accuracy suite — a "completed" status would falsely green regardless of mixer correctness. Instead pin the exact non-linear-DAC behaviour those ROMs exercise as **deterministic property unit tests** at the `mixSample` level: square cross-attenuation (a second pulse adds less than the first), tnd cross-attenuation (the DMC DAC attenuates the triangle through the shared tnd term), and pulse/tnd group independence. Document that the **expansion chips (Sunsoft 5B / VRC6 / VRC7 / MMC5) sum as post-DAC int16 addends** — they mix on the cart's analog out, not through the 2A03 DAC.
- **Consequences:** the DAC is regression-locked by fast, deterministic tests that can't false-pass, and CLAUDE.md records why `apu_mixer` is deliberately absent so it isn't re-litigated. Closed #5.

## D6 — Perfgate: a hardware-absolute baseline calibrated to the CI runner, not a dev machine

- **Context:** the per-cycle CPU↔PPU interleave is the emulator's hot path; a silent regression toward sub-60fps on older hardware is exactly the kind of drift a test suite doesn't catch. chippy has a `perf baseline` job to port, but `ns/op` is hardware-absolute — a baseline recorded on Apple Silicon (which runs these ~5× realtime) would be far too tight for the ubuntu-latest runner that enforces it.
- **Decision:** add a `perfgate`-tagged `TestPerfGate` (`cmd/nessy-record`, headless — no Ebiten) that benchmarks steady-state per-frame cost on three committed demo ROMs, each a distinct hot path (BG-only, full sprite eval, MMC3 scanline-IRQ + scroll), and fails on a **>10% ns/frame regression** vs a committed ceiling. The **baseline is reseeded from the ubuntu-latest CI run itself** (observed ns/frame + a ~5% noise cushion), never a dev box; the recipe lives in `docs/perf-baseline.md`. The job logs the realtime multiple so 60fps headroom is visible.
- **Consequences:** the interleave is guarded against regression on the same runner class that enforces it (~4.7× realtime headroom on ubuntu today). The "vacuously green" perfgate slot from ADR 0008's CI foundation is now a real gate. Closed #11.

## D7 — WASM playground: a thin Go API, the UX lives in JS

- **Context:** the browser build (`cmd/nessy-wasm`, ADR 0006) loaded a default ROM and rendered — no file picker, gamepad, save slots, or offline support. Bringing it to desktop parity is mostly front-end work that has no place in Go.
- **Decision:** keep the Go core a **thin API surface** — `nessy.{loadROM, setButton, setKeyboard, screenshot, saveState, loadState, romHash}` — and put the whole UX in a plain-JS shell (`web/nessy/app.js`): file-picker + drag/drop ROM load, standard-mapping gamepad polling, a keyboard-remap wizard (persisted; `setKeyboard` hands the JS shell full ownership of the keyboard), IndexedDB save slots keyed by ROM hash, PNG screenshot (pulled from the core framebuffer — Ebiten's WebGL canvas reads back empty), fullscreen, and a PWA service worker for offline. **Save-state reuses the desktop subsystem serialization** (`SaveFullState`/`LoadFullState` + gzip(gob)) with a magic/version + ROM-hash guard, so a browser slot is the same format as a desktop `.state`.
- **Consequences:** all six #10 tasks shipped. Browser behaviour isn't reachable in CI, so the gate is the wasm build plus a `node --check` of the shell JS + manifest JSON. Closed #10.

## D8 — Hand-roll the release pipeline; goreleaser can't ingest the Ebiten CGO binaries

- **Context:** chippy releases via goreleaser, cross-compiling every target on one runner because it's pure-Go (`CGO_ENABLED=0`). **nessy is an Ebiten CGO app** — it can't cross-compile from a single runner, and goreleaser's OSS build can't ingest externally-built CGO binaries: the `prebuilt` builder was removed, and split/merge is Pro-only (confirmed across v2.5-v2.16).
- **Decision:** **hand-roll `.github/workflows/release.yml`** to produce the same artifact shape as chippy without goreleaser. A **per-OS native build matrix** (macOS arm64 + intel, Linux amd64 + arm64, Windows) builds each target, then a finalize job archives, checksums, **keyless-cosign** signs every artifact, attaches **syft SPDX SBOMs**, builds `.deb`/`.rpm`/`.apk` via **nfpm** (with the GL/X11/ALSA runtime deps the CGO binary needs), and publishes the GitHub release. Homebrew cask + AUR run on **stable tags only** — a `-` in the tag marks a prerelease, which skips them, so an `-rc` tag is a secret-free end-to-end smoke test. Version is stamped via `-X main.version/commit/date` ldflags.
- **Consequences:** the pipeline is built + smoke-tested (a `v0.9.0-rc.1` prerelease produced the full artifact set; `cosign verify-blob` → Verified OK; Homebrew/AUR auto-skipped). It stays open (#8) only until the two stable-release secrets (`HOMEBREW_TAP_GITHUB_TOKEN`, `AUR_SSH_PRIVATE_KEY`) are added + a stable `v1.0.0` tag validates the Homebrew/AUR jobs. Playbook: `docs/RELEASE.md`.

## D9 — The two-repo dependency edge in practice: host hooks, a staged core fix, and resyncs

- **Context:** ADR 0008 D1 called the chippy carve-out's cost a "two-repo dependency edge: a CPU-core fix now requires a chippy release + a `go.mod` bump." v1.0 is where that edge got exercised in anger.
- **Decision:** consume chippy deliberately. The debugger epic (D1) is unblocked by pulling the **v1.5.0 host hooks**. The dmc_dma #20 fix needed a genuine CPU-core change (`idle()` polling `ProcessPendingDma`, D3) — landed as chippy #497, released as **v1.8.0**, and **staged behind a temporary `go.mod replace`** pointing at a local chippy checkout so nessy's row went green before the tag existed, then swapped for the real `require` once released. Routine resyncs (most recently to **v1.12.0**) are validated against the accuracy suite + perfgate before merging — the v1.9-1.12 chippy work is almost entirely 65816, a CPU nessy doesn't use, so the NES path is untouched.
- **Consequences:** the edge is managed, not painful: host hooks arrive as minor bumps, a core fix follows the replace→release→bump dance, and the accuracy suite is the gate that makes a bump safe to merge. `CLAUDE.md`'s "Chippy library dependency" section enumerates the exact public API nessy leans on.

## Note

The invariants behind these decisions are codified in this repo's `CLAUDE.md`: the debugger protocol + the five accuracy-grading paths + the MMC5 PPU seam + the perfgate baseline discipline all have dedicated sections there, and the accuracy harness (`cmd/nessy/accuracy_test.go`) + `TestPerfGate` are the executable record that the cycle-precision and performance work still holds. As with ADR 0008, the chippy-side pieces (D2's `IRQAsserted`, D3's `idle()`/`ProcessPendingDma` fix, D9's host hooks) live in the `github.com/nkane/chippy` dependency pinned in `go.mod`; the nessy-side pieces live in `internal/nes` + `cmd/nessy`. The remaining v1.0 gates are the #7 headliner playtest and the #8 stable-release secrets — both outside the code, both tracked on their issues.
